01

Phase based day and night cycle

Lighting Client prediction Config driven

Roblox quantises ClockTime, so a slow continuous cycle visibly steps no matter how often you write to it. This one holds the sun still through day and night and only animates the transitions, fast enough that they stay smooth. The server publishes a single time anchor and each client derives the hour locally, so there is one writer and no replication jitter.

DayNightData.lua 
local DayNightData = {}

DayNightData.DAY_HOUR   = 13
DayNightData.NIGHT_HOUR = 23
DayNightData.DAY_HOLD   = 300  -- seconds held at noon
DayNightData.NIGHT_HOLD = 150
DayNightData.TRANSITION = 20   -- dusk / dawn length
DayNightData.EASE_BLEND = 0.7

-- sun and moon sit 12h apart on one track, so these two
-- must NOT be 12 apart or the moon parks where the sun was
function DayNightData.ArcHours()
	return (DayNightData.NIGHT_HOUR - DayNightData.DAY_HOUR) % 24
end

local function smoothstep(t)
	return t * t * (3 - 2 * t)
end

-- a full ease starts and ends at zero speed, which is
-- exactly what stutters. blend a linear floor underneath.
function DayNightData.Ease(t)
	return t * (1 - DayNightData.EASE_BLEND)
		+ smoothstep(t) * DayNightData.EASE_BLEND
end

-- shared, so server and client run identical maths
-- from the one replicated anchor
function DayNightData.HourAt(elapsed)
	-- returns hour, phase ("Day"/"Dusk"/"Night"/"Dawn")
end

return table.freeze(DayNightData)

02

XP and levelling

Progression HUD Balancing

XP comes from several different activities, and each payout is scaled by what the player actually did rather than a flat number per action. Awards hook in only where the action genuinely succeeded, so something the game refuses pays nothing. The curve sits in one shared module that the HUD bar reads from as well, which leaves a single place it can be wrong and makes rebalancing a number change.

XPData.lua 
local XPData = {}

XPData.MAX_LEVEL = 500

-- gentle quadratic: 100 / 125 / 175 / 244 ... 1095 at L10
function XPData.Requirement(level)
	return math.floor(100 + 25 * level ^ 1.6)
end

-- sqrt so a 40kg item beats a 2kg one without being 20x
function XPData.Harvest(weight, modifiers)
	local base = 8 + 4 * math.sqrt(weight)
	return math.floor(base * (1 + modifiers * 0.5))
end

XPData.Rarity = {
	common = 1,      uncommon = 1.4, rare   = 2,
	legendary = 3,   mythical = 4.5, exotic = 6,
	radiant = 8,
}

function XPData.Catch(weight, rarity)
	local mult = XPData.Rarity[rarity] or 1
	return math.floor((12 + 3 * math.sqrt(weight)) * mult)
end

-- deliberately the thinnest source: selling already pays
-- out, it should not also be the fastest way to level
function XPData.Sale(payout)
	return math.clamp(math.floor(payout * 0.02), 1, 400)
end

return table.freeze(XPData)

03

Tier weighted loot and spawning

Loot tables Spawning Economy

Containers and collectibles spawn inside a marker volume using rejection sampling, so they only ever land on valid ground. Move or resize that marker in Studio and nothing in code changes. Rarity rolls by tier first and then uniformly inside it, which stops the largest tier quietly dominating the odds. The item pool is derived from data the game already owns rather than restated, so a newly added item cannot silently fail to drop.

LootData.lua 
local LootData = {}

LootData.Tiers = {
	"Common", "Uncommon", "Rare", "Epic",
	"Legendary", "Mythical", "Exotic",
}

-- roll the TIER first, then uniformly inside it, so the
-- tier holding the most items cannot dominate the odds
LootData.Containers = {
	Bronze = {
		MaxAlive = 6, Respawn = 45, Rewards = 1,
		TierWeights = {
			Common = 62, Uncommon = 24,
			Rare = 11, Epic = 3, Legendary = 1,
		},
	},
	Gold = {
		MaxAlive = 2, Respawn = 180, Rewards = 3,
		TierWeights = {
			Common = 8,  Uncommon = 17, Rare = 27,
			Epic = 26, Legendary = 15,
			Mythical = 6, Exotic = 1,
		},
	},
}

-- spawn area is a marker part; resize it freely, no code change
LootData.Area = {
	Path = { "LootSpawns", "Area01" },
	RequiredMaterial = Enum.Material.Sand,
	ColorTolerance   = 0.02,
	MaxSpawnAttempts = 40,
}

LootData.Prompt = {
	Style = Enum.ProximityPromptStyle.Custom,
	KeyboardKeyCode = Enum.KeyCode.E,
	HoldDuration = 0.25,
	RequiresLineOfSight = false,
}

return table.freeze(LootData)

04

NPC behaviour and melee combat

AI Server authoritative Performance

NPCs wander, aggro, chase and attack without PathfindingService. One throttled loop steps every NPC instead of a thread each, which is what keeps it cheap as the count grows. The melee hitbox queries the NPC collection only, so it is structurally unable to hit a player rather than relying on a check that could be written wrong. The attack remote carries no arguments at all: the server reads the attacker's own position and revalidates range and cooldown itself.

CombatData.lua 
local CombatData = {}

-- shared so the client can predict feel, but every value is
-- re-read SERVER side when used, so a tampered copy does nothing
CombatData.Melee = {
	Damage         = 25,
	Cooldown       = 0.55,
	HitboxRadius   = 6,
	HitboxDistance = 4,
	Knockback      = 35,
	MaxHitDistance = 14,
}

CombatData.NPCs = {
	Grunt = {
		Health       = 100,
		WalkSpeed    = 6,
		ChaseSpeed   = 14,
		Damage       = 10,
		AttackRange  = 7,
		AggroRange   = 45,
		-- deliberately LARGER than AggroRange; one shared
		-- value makes an NPC on the boundary flip every tick
		DeaggroRange = 60,
		LeashDrop    = 25,
		RespawnDelay = 20,
	},
}

-- one throttled loop steps every NPC, not a thread each
CombatData.TickRate = 0.15

return table.freeze(CombatData)

03 Capabilities

What I take from setup to delivery

Admin and moderation tooling

Console commands with rank based permissions resolved from group role, argument autocomplete that will not suggest anything the command would go on to refuse, and DataStore backed records kept as an audit log that never gates anything on its own.

Data and persistence

Profile based saving with careful load and release ordering, plus separate stores for the cases where a profile's session lock gets in the way. Inventory layout, settings and unlocked titles all survive a rejoin, validated server side so a client can only rearrange its own things.

Config driven gameplay

Cooldowns, movement feel, progression pacing and combat feedback kept in exposed tables, so a designer can rebalance without opening the logic and an iteration is a number change rather than a rewrite.

Refactoring and cleanup

Turning copy pasted scripts into one service that finds its own stations by structure, so adding another needs no code. Per instance differences move into attributes, and the originals stay disabled rather than deleted so the change can be undone.

Interface and HUD work

Settings menus, hotbar and inventory handling, overhead nameplates and progress bars, wired so the server stays the source of truth and the interface reflects replicated state instead of keeping its own copy.

Debugging and live verification

The bugs that do not reproduce on paper: replication fighting client side smoothing, frame of reference mismatches, ordering traps during startup. I check the fix in a running session and measure the result rather than calling it done.
