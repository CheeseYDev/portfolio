Phase-Based Day / Night Cycle

Lighting Client Prediction Config-Driven

Roblox quantises ClockTime, so a slow continuous cycle visibly steps no matter how often you write it. This holds the sun still through day and night and only animates the transitions — fast enough to stay smooth. The server publishes a single time anchor; each client derives the hour locally, so there's one writer and no replication jitter.

DayNightData.lua 
local DayNightData = {}

DayNightData.DAY_HOUR   = 13
DayNightData.NIGHT_HOUR = 23
DayNightData.DAY_HOLD   = 300  -- seconds held at noon
DayNightData.NIGHT_HOLD = 150
DayNightData.TRANSITION = 20   -- dusk / dawn length
DayNightData.EASE_BLEND = 0.7

-- sun and moon sit 12h apart on one track, so the hours
-- must NOT be 12 apart or the moon parks where the sun was
function DayNightData.ArcHours()
	return (DayNightData.NIGHT_HOUR - DayNightData.DAY_HOUR) % 24
end

local function smoothstep(t)
	return t * t * (3 - 2 * t)
end

-- a full ease starts and ends at zero speed, which is exactly
-- what stutters. blend a linear floor underneath it.
function DayNightData.Ease(t)
	return t * (1 - DayNightData.EASE_BLEND)
		+ smoothstep(t) * DayNightData.EASE_BLEND
end

-- shared, so server and client run identical maths
-- off the one replicated anchor
function DayNightData.HourAt(elapsed)
	-- returns hour, phase ("Day"/"Dusk"/"Night"/"Dawn")
end

return table.freeze(DayNightData)

XP & Levelling System

Progression HUD Balancing

A progression system that pulls XP from several different activities, each payout scaled by what the player actually did rather than a flat number per action. Awards hook in only on genuine success, so an action the game refuses pays nothing. The curve lives in one shared module that the HUD bar reads from too, so there's a single place it can ever be wrong — and rebalancing is a number change, not a rewrite.

XPData.lua 
local XPData = {}

XPData.MAX_LEVEL = 500

-- gentle quadratic: 100 / 125 / 175 / 244 ... 1095 at L10
function XPData.Requirement(level)
	return math.floor(100 + 25 * level ^ 1.6)
end

-- sqrt so a 40kg fruit beats a 2kg one without being 20x
function XPData.Harvest(weight, mutations)
	local base = 8 + 4 * math.sqrt(weight)
	return math.floor(base * (1 + mutations * 0.5))
end

XPData.FishRarity = {
	common = 1,      uncommon = 1.4, rare   = 2,
	legendary = 3,   mythical = 4.5, exotic = 6,
	radiant = 8,
}

function XPData.Fish(weight, rarity)
	local mult = XPData.FishRarity[rarity] or 1
	return math.floor((12 + 3 * math.sqrt(weight)) * mult)
end

-- deliberately the thinnest source: selling already
-- pays out, it shouldn't also be the fastest way to level
function XPData.Sale(payout)
	return math.clamp(math.floor(payout * 0.02), 1, 400)
end

return table.freeze(XPData)

Tier-Weighted Loot & Spawning

Loot Tables Spawning Economy

Collectibles and containers spawn inside a marker volume using rejection sampling, so they only ever land on valid ground — move or resize the marker in Studio and nothing in code changes. Rarity is rolled by tier first, then uniformly inside it, so the largest tier can't quietly dominate the odds. The item pool is derived from data the game already owns rather than restated, which means a newly added item can't silently fail to drop.

LootData.lua 
local LootData = {}

LootData.Tiers = {
	"Common", "Uncommon", "Rare", "Epic",
	"Legendary", "Mythical", "Exotic",
}

-- roll the TIER first, then uniformly inside it, so the
-- tier holding the most items can't dominate the odds
LootData.Chests = {
	Bronze = {
		MaxAlive = 6, Respawn = 45, Rewards = 1,
		TierWeights = {
			Common = 62, Uncommon = 24,
			Rare = 11, Epic = 3, Legendary = 1,
		},
	},
	Gold = {
		MaxAlive = 2, Respawn = 180, Rewards = 3,
		TierWeights = {
			Common = 8,  Uncommon = 17, Rare = 27,
			Epic = 26, Legendary = 15,
			Mythical = 6, Exotic = 1,
		},
	},
}

-- spawn area is a marker part; resize it freely, no code change
LootData.Area = {
	Path = { "LootSpawns", "Area01" },
	RequiredMaterial = Enum.Material.Sand,
	ColorTolerance   = 0.02,
	MaxSpawnAttempts = 40,
}

LootData.Prompt = {
	Style = Enum.ProximityPromptStyle.Custom,
	KeyboardKeyCode = Enum.KeyCode.E,
	HoldDuration = 0.25,
	RequiresLineOfSight = false,
}

return table.freeze(LootData)

NPC AI & Melee Combat

AI Server-Authoritative Performance

NPCs that wander, aggro, chase and attack without PathfindingService — one throttled loop steps every NPC instead of a thread each, which is what keeps it cheap at scale. The melee hitbox queries the NPC collection only, so it is structurally unable to hit a player rather than relying on a check that could be wrong. The attack remote carries no arguments at all: the server reads the attacker's own position and re-validates range and cooldown itself.

CombatData.lua 
local CombatData = {}

-- shared for feel, but every value is re-read SERVER-side
-- when used, so a tampered client copy changes nothing
CombatData.Knife = {
	Damage         = 25,
	Cooldown       = 0.55,
	HitboxRadius   = 6,
	HitboxDistance = 4,
	Knockback      = 35,
	MaxHitDistance = 14,
}

CombatData.Mobs = {
	Grunt = {
		Health       = 100,
		WalkSpeed    = 6,
		ChaseSpeed   = 14,
		Damage       = 10,
		AttackRange  = 7,
		AggroRange   = 45,
		-- deliberately LARGER than AggroRange; one shared
		-- value makes a mob on the boundary flip every tick
		DeaggroRange = 60,
		LeashDrop    = 25,
		RespawnDelay = 20,
	},
}

-- one throttled loop steps every mob, not a thread each
CombatData.TickRate = 0.15

return table.freeze(CombatData)
